01 · System design

How the controller thinks

Every polling interval, the controller repeats a five-stage loop — the same loop a Ryu/ONOS application would run against real OpenFlow switches.

STEP 1

Collect flow stats

Switches report packet size, inter-arrival time, duration and demand for every active flow.

→
STEP 2

Classify traffic

A Random Forest labels each flow as voice, video, web or bulk, and assigns a QoS priority.

→
STEP 3

Forecast congestion

A regressor predicts next-interval utilization per link from recent history, before it saturates.

→
STEP 4

Compute adaptive paths

Dijkstra re-weights every link by real-time load + forecast + flow priority, then re-routes.

→
STEP 5

Push flow rules

New OpenFlow rules are installed on switches along the chosen path for that flow.

03 · Machine learning

Two models power the controller

Both are trained offline on synthetic flow data with realistic per-application statistical signatures, then used online for every controller decision.

Traffic classifier — Random Forest

Input features: average packet size, inter-arrival time, flow duration, demand (Mbps) and packet count. Output: application class + QoS priority.

Congestion predictor — RF Regressor

Input: last 4 intervals of a link's utilization (%). Output: forecasted utilization for the next interval, used to steer new flows away before saturation happens.

05 · Real deployment

Validated on an actual SDN stack

Beyond the simulation above, the same routing logic runs as a real controller against real Mininet switches, real Open vSwitch, and real OpenFlow 1.3 messages (via os-ken, the maintained Ryu-API-compatible framework). This is the captured output of an actual run: the s2–s4 link is saturated with a real 60 Mbps bulk transfer, then a new latency-sensitive flow is opened while that congestion is happening.

Static controller — blind to load

[static] 10.0.0.2 -> 10.0.0.4 routed via switches [2, 4, 7, 6]
    ← bulk transfer saturates link s2–s4
[static] 10.0.0.2 -> 10.0.0.5 routed via switches [2, 4, 7]
    ← new voice flow sent through it anyway

AI-adaptive controller — reacts to real telemetry

[adaptive] 10.0.0.2:55367 -> 10.0.0.4:5001 class=bulk priority=4 path=[2, 4, 7, 6]
[adaptive][live-ML] flow classified as 'bulk'
    (demand=61.50Mbps, pkt_size=1512B, duration=7.5s)
[adaptive] 10.0.0.2:50331 -> 10.0.0.5:5060 class=voice priority=1 path=[2, 5, 7]
    ← rerouted around the congested link

The [live-ML] line is the pretrained Random Forest classifier running on real byte/packet counters pulled mid-transfer from the switches via OFPFlowStatsRequest — not synthetic data. Full setup + how to reproduce this yourself: mininet_sdn/README_MININET.md.

05 · Takeaways

What this demonstrates

Traffic-aware routing works

Knowing whether a flow is voice or bulk transfer — and treating it differently — measurably cuts latency for delay-sensitive traffic.

Prediction beats reaction

Forecasting link utilization one step ahead lets the controller avoid congestion before it happens, rather than after packets are already dropped.

SDN makes it possible

A centralized controller with a global view can recompute optimal paths per-flow in real time — something distributed static protocols like OSPF cannot do.
